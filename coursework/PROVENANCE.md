# Sources and adoption decision

The complete official [NATS server](https://github.com/nats-io/nats-server) repository was cloned without shallow history on 2026-10-21. The selected stable [v2.15.1 release](https://github.com/nats-io/nats-server/releases/tag/v2.15.1) resolves to `b2fd3efc7456b11b06a54877ad6f6ccfb911edb4`. Its 13,394 ancestor commits are retained at the adoption point. `git rev-parse --is-shallow-repository` returns `false`. Only the `upstream` remote exists before publication by the main agent.

The Apache-2.0 `LICENSE`, upstream notices, authors, public module path and core server implementation remain intact. The original README is preserved byte-for-byte as a Git blob in `README.upstream.md`. Upstream workflow files are moved to `.github/upstream-workflows/` with one inactive-reference comment. No release or deployment workflow is active. New Go code reuses the already pinned official `github.com/nats-io/nats.go v1.53.1` client, also Apache-2.0. `go.mod` and `go.sum` are unchanged. Python uses only its standard library.

The [KiraraMQ Stanford CS244b report](https://www.scs.stanford.edu/24sp-cs244b/projects/KiraraMQ_A_Lightweight_Fault_Tolerant_and_Distributed_Message_Queue.pdf) is the course evidence. Its named student repository was unavailable when the main agent checked it. No inaccessible student source is copied or represented as reproduced. This adaptation retains topics, channel fanout, shared consumers and acknowledgment timeout semantics, then studies durable replicated-log recovery using JetStream's existing Raft groups. It does not implement KiraraMQ's etcd discovery or gRPC consumption API.

[Kafka's 2011 paper](https://notes.stephenholiday.com/Kafka.pdf) supplies the durable-log research connection. The adaptation's bounded HTTP interface, portable client, accepted-write ledger and controlled failure scenarios are new work. Replication, consensus, disk storage and native delivery mechanisms are upstream work. This is an engineering adaptation, not a novel consensus algorithm or an exact university assignment solution.

The official [pull-consumer documentation](https://docs.nats.io/learn/jetstream/pull-consumers) and [cluster documentation](https://docs.nats.io/learn/topologies/jetstream-in-a-cluster) informed the stream/channel mapping. The current stable release, existing dependency pins, local build and actual multi-process proof establish source/platform compatibility. The upstream [security advisory index](https://github.com/nats-io/nats-server/security/advisories) was reviewed. For example, [GHSA-q59r-vq66-pxc2](https://github.com/nats-io/nats-server/security/advisories/GHSA-q59r-vq66-pxc2) lists patched versions 2.14.3 and 2.12.12, older than this pin. This is a bounded adoption review, not a claim of a complete vulnerability audit. Keep the local capability API on loopback and reevaluate upstream advisories before remote deployment.

Verification follows the Prove It Works principle using real broker processes and HTTP calls. Model the Domain shaped the direct topic-to-stream and channel-to-durable-consumer mapping, with a typed namespace-bound receipt. Ponytail favored the existing official client and storage mechanisms over new protocol or consensus code. No additional dependencies, panels, UI, Docker, GPU support or public deployment were added.
